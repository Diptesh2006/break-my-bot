# Integration boundaries

## Turbulence adapter

Turbulence remains an independently versioned FastAPI/Next.js product. Its current deterministic injector evaluates faults at the Concentrate client boundary. The simulator creates simulated provider faults; they are not incidents in the target application. Its agent safety outcomes use fixtures and are likewise not external-target observations.

BreakMyBot's run model stores target endpoint, observed status/body evidence, measured latency, explicit assertions, and unsupported capabilities. Its opt-in `instrument(app, token=..., enabled=True)` adapter provides a protected session control API. The target must route tool calls through `controller.invoke(...)`; middleware scopes those calls using `X-BreakMyBot-Session`. BreakMyBot verifies the contract, arms one bounded session containing a single fault or an ordered multi-tool fault chain, invokes the target, reads the target's actual injection events, then attempts cleanup. Tool results count only when all configured faults are confirmed in order and cleanup succeeds; without an explicit invariant they remain inconclusive. The control token is never included in run evidence. This is opt-in and does not instrument arbitrary apps that have not installed the adapter.

Turbulence remains independently versioned and its fault engine continues to act at its own Concentrate client boundary. Its `GET /api/integrations/breakmybot/capabilities` manifest advertises provider-boundary simulation but explicitly reports external-target tool injection and an HTTP fault proxy as unsupported. The manifest is a compatibility/scope contract, not an instruction for BreakMyBot to import Turbulence simulator outcomes. Turbulence is not yet a pluggable BreakMyBot `FaultEngine`. Sharing target results requires an explicit, target-scoped adapter contract with injection provenance and cleanup evidence. There are no absolute filesystem imports or copied Turbulence demo results.

## MemoryScope adapter

MemoryScope remains an independently versioned local beta at `Desktop/proj/MemoryGuard`. Its `/api/beta/capabilities` endpoint advertises the versioned `memoryscope-answer-evaluation-v1` contract. The supported capability is grounded answer evaluation against an external SSE endpoint; persistent memory lifecycle and tenant isolation are explicitly false. It requires explicit consent and a configured server-side LLM judge, and persists evidence locally. MemoryScope lifecycle seed/reset adapters are not implemented; archived synthetic memory experiments are not external-target evidence.

BreakMyBot has an optional API bridge. The operator provides `MEMORYSCOPE_API_URL`, an SSE-compatible path on the selected target's same origin, approved reference cases, judge credentials/model in the MemoryScope server environment, and explicit consent before data is sent. The bridge checks the capability contract and judge readiness, starts and polls an actual MemoryScope run, then imports its per-case answer and grounded judge evidence into the BreakMyBot run. Missing services, incompatible contracts, or configuration produce setup errors; denied consent skips the evaluation. This evaluates answer correctness, not persistent memory state. Separately, BreakMyBot includes a built-in reference-grounded semantic judge for operator-supplied case payloads; it does not require MemoryScope.

Persistent-memory experiments use BreakMyBot's separate opt-in target contract in `docs/memory-adapter.md`. The target owns callbacks to snapshot, seed, and restore its actual memory store; only explicitly advertised categories are exercised. A scenario is scored only after real target invocation(s), literal invariants, and confirmed restoration. Without an adapter or category support, the report marks each category `UNSUPPORTED` / `NOT TESTED — memory interface unavailable`. The bundled demo advertises only its stale-knowledge fixture. MemoryScope's internal experiments are never substituted for evidence from the selected target.

## Scenario-planner provider contract

nRouter is the default and primary MVP provider for BreakMyBot's structured investigator and scenario planner; it uses `NROUTER_API_KEY`, `NROUTER_BASE_URL`, and `BREAKMYBOT_PLANNER_MODEL`. Named OpenAI-compatible presets are also provided for OpenAI, OpenRouter, Groq, Gemini, Mistral, and DeepSeek. Each resolves its documented API base and conventional provider key environment variable; model IDs are operator-selected. Any other OpenAI-compatible chat-completions service can use `BREAKMYBOT_LLM_PROVIDER=openai-compatible`, `BREAKMYBOT_LLM_BASE_URL`, and either a direct `BREAKMYBOT_LLM_API_KEY` or a `BREAKMYBOT_LLM_API_KEY_ENV` reference to a secret environment variable. The model may be supplied as `BREAKMYBOT_LLM_MODEL` or `BREAKMYBOT_PLANNER_MODEL`; compatible gateways can customize the auth header/scheme, path, and completion-token parameter. Native-only APIs that do not implement OpenAI-compatible chat completions are not supported by these presets. Non-loopback provider URLs must use HTTPS. The configured provider name, model, and provider-returned usage/cost are recorded; credentials are not. When credentials are configured, the CLI and dashboard offer the investigator/planner by default and request per-run consent; `--no-plan-with-ai` skips it in the CLI. No configured provider or denied consent keeps the run on the deterministic path. After consent, the model is called only after a target HTTP baseline exists; it receives bounded endpoint schemas/descriptions, payload field names, and baseline status/latency/content type/response size/contract outcome, but not payload values or response text. If no HTTP observation is available, no model call is made. Findings and scenario proposals are hypotheses, do not contribute to scoring, and remain unexecuted by default. A separate `--execute-planned-scenarios` opt-in requires accepted target instrumentation, an explicit expected-response oracle, and the operator-approved tool/fault and oracle allowlists. Non-GET calls also require repeated-call safety authorization. Provider failure never falls back to executing unvalidated proposals. Automated tests cover provider configuration, transport restrictions, key redaction, proposal validation, and instrumented execution; no live paid-provider smoke test has been verified in this environment. The optional MemoryScope evaluator is independent and uses its own server-side judge configuration.
